# 项目开发流程

## 三层职责

项目以“用户意图 → 架构决策 → 源码实现”组织开发。架构设计与功能实现都服务于用户原始需求。

| 层次 | 回答的问题 | 内容边界 |
| --- | --- | --- |
| [用户需求](features/README.md) | 用户为什么需要这项能力，希望完成什么？ | 高层次目标、使用场景，以及表达使用行为的示例 |
| [架构规范](architecture/README.md) | 为达成需求，系统如何划分职责并约定行为？ | 包与模块分层、职责边界、行为契约、类型规则及实现 specification |
| 源代码与测试 | 架构决策如何落地，是否实现了用户意图？ | 可执行实现，以及对用户行为、架构契约和类型约束的验证 |

一项需求可能由多个模块共同实现，一个模块也可能支撑多项需求。设计时应能说明其服务的用户目标，验证时应能回到用户场景判断是否达成。

## 需求文档写法

每个场景先用简短文字说明用户是谁、希望达成什么，再依次提供：

1. **代码示例**：通过公开能力编写的最小使用示例。
2. **使用示例**：将用户操作与终端输出、任务效果、错误反馈或开发时提示放在一起，命令后直接展示对应结果。

原始意图保持高层次，描述用户目标。代码示例使用公开 API 和应用自己的业务逻辑；框架内部设计与实现规则由架构文档承载。

从命令行参数与选项解析的使用需求出发，优先通过真实命令行操作展示用户完成任务的效果。

示例保持直接、简短，让操作和结果本身表达需求。

新增或尚未实现的需求应明确标注状态，示例区分拟议用法与已有能力。需求以确认的用户意图为依据。

## 变更顺序

1. **理解意图**：先阅读相关需求，再核对架构、实现、测试和用户文档，确定用户要解决的问题以及本次变更范围。
2. **明确需求变化**：新增能力或改变用户可见行为时，先补充或修改需求场景与示例。需求未变化的修复和内部重构，保持原始意图稳定。
3. **形成架构决策**：确定职责归属、行为契约和类型约束，检查方案是否服务需求。尚未落地的设计在变更说明中表达；架构基线只描述已经实现的设计。
4. **实现与验证**：按架构决策完成代码及必要测试。将需求中的预期行为转化为验证依据，同时覆盖相关错误路径和类型约束。
5. **同步交付**：将已落地的设计更新到架构规范；用户操作有变化时同步用户文档。核对三层一致性，运行适用检查，说明验证结果及未完成项。

## 冲突处理

需求、架构和实现不一致时，先判断用户意图是否仍然成立。若意图未变，应调整架构或实现；若意图确实改变，应先更新需求，再决定后续设计。

无法从任务和现有资料判断预期时，明确列出冲突与待确认的用户行为，向需求提出者确认后再写入需求文档。

## 完成条件与维护

- 用户意图有清晰表达；新增或改变的使用行为有对应示例和预期结果。
- 已实现的架构、源码、类型与测试共同支撑该意图；未完成能力有明确状态。
- 操作有变化时，使用者能从用户文档获得一致指引。
- 适用检查已经完成，交付说明包含验证结果与尚存差异。

文档直接描述当前有效内容。索引负责导航，流程规则集中在本文。移动或删除文档时同步修复引用。
